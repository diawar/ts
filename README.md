# Госзакупки

Поиск закупок Казахстана: общая база активных лотов, поиск по названиям и дополнительным описаниям, персональные подборки, избранное и Telegram-уведомления.

Актуальные требования, архитектура и ограничения: [ТЗ для ИИ-агента](AI_AGENT_TECHNICAL_SPECIFICATION.md). `TECHNICAL_SPECIFICATION.md` и `docs/stage-*.md` отражают ранние этапы.

## Что работает

- Поиск по нескольким словам с И/ИЛИ, настройкой совпадения и исключениями.
- Флажок «Только с авансом» (по умолчанию выключен), сохранение в подборке и зелёная плашка выбранного условия. Признак определяется по положительному `prepayment` в пунктах плана или их `specifics`; неизвестное значение не считается подтверждённым авансом. При обновлении существующей установки выполните `docker compose run --rm --no-deps web python manage.py backfill_advance_flags`, чтобы заполнить признак из сохранённых ответов API без повторной загрузки.
- Фильтры статусов, способов закупки, суммы, сроков, области/города, БИН и номера.
- Личные подборки и избранное; таблица и карточки результатов.
- Круглосуточное накопление активных статусов источника 6/7/9 с неистёкшим сроком подачи, включая ожидающие начала приёма. Все способы закупки собираются независимо от фильтров пользователей.
- Поиск по накопленной базе без ограничения глубины в отдельной очереди.
- Telegram: проверки и рассылки подборок с 07:00 до 19:00 по Алматы; статусные уведомления и ручные действия — круглосуточно.
- Скачивание документов при добавлении в избранное; удаление файлов после удаления последнего связанного избранного.

Первоначальный сбор может занимать часы. Панель поиска показывает состояние базы и непроверенные описания. Неполный результат не доказывает отсутствия закупки на портале. Полный архив не загружается; физическая очистка старых записей пока не включена. Поиск внутри файлов и OCR ещё не реализованы.

Если карточка объявления возвращает HTTP 404, сборщик сохраняет лоты из реестра и продолжает обход. Их дополнительные описания отмечаются непроверенными и запрашиваются повторно позже; пока такие активные лоты остаются, полнота базы не подтверждается. Ошибка самого реестра, доступа, сети или формата ответа сохраняет курсор страницы для повторной попытки.

## Запуск на новом компьютере

Подробный порядок новой установки, обновления, переноса данных и настройки HTTPS: [инструкция для ИИ-агента](docs/AGENT_INSTALLATION.md).

Нужны Git, Python 3.11+ и Docker с Compose. На Windows — Docker Desktop с WSL 2.

```powershell
git clone https://github.com/diawar/tendersearch.git
cd tendersearch
python scripts/setup_local.py
docker compose up -d --build
docker compose exec web python manage.py sync_references
docker compose exec web python manage.py sync_cities
```

Приложение: [http://localhost:8000](http://localhost:8000).

`setup_local.py` создаёт `.env` со случайными секретами и `data/first-login.txt` с данными первого входа. Существующие настройки не перезаписываются. `initialize` применяет миграции и создаёт администратора, сохраняя пароль уже существующего пользователя.

Самостоятельная регистрация закрыта. Пользователь с ролью «Администратор» видит раздел «Администрирование»: таблицу всех пользователей, создание, редактирование (включая смену роли, пароля и отключение доступа) и удаление с подтверждением. При удалении убираются личные данные и отслеживание пользователя; общие лоты сохраняются. Учётную запись admin нельзя удалить, переименовать или отключить. Пароль сохраняется через стандартное хеширование Django. Доступны две роли: «Пользователь» и «Администратор». Старый признак staff без прав суперпользователя трактуется как «Пользователь». Обычные пользователи не имеют доступа к разделу и блоку «База активных закупок».

Это запуск с новой базой. Пользователи, подборки, избранное, Telegram-привязки и документы прежней установки требуют отдельного защищённого переноса PostgreSQL, тома документов и локальных настроек. В GitHub эти данные не включаются.

## Telegram

Создайте отдельного бота «Госзакупки» через @BotFather. Добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` в локальный `.env`, ориентируясь на `.env.example`, затем выполните:

```powershell
docker compose up -d web worker search-worker indexer detail-indexer telegram
```

Подключение пользователя выполняется через одноразовую ссылку в настройках приложения. Уведомления включаются отдельно для каждой подборки. Первый обход запоминает исходную выдачу без рассылки архивных объявлений.

## Службы и данные

| Служба | Назначение |
| --- | --- |
| `web` | Django, Gunicorn, HTMX, статические файлы |
| `search-worker` | Ручные поиски, очередь `interactive` |
| `worker` | Мониторинг, карточки и документы, очередь `celery` |
| `indexer` | Быстрый обход реестров лотов и объявлений, без загрузки подробностей |
| `collection-monitor` | Планирование обновления сохранённых подборок, независимо от Telegram |
| `detail-indexer` | Устойчивая очередь подробностей объявлений; новые и изменённые — в первую очередь |
| `telegram` | Планирование проверок и доставка уведомлений |
| `db`, `redis` | PostgreSQL 17 и Redis 7 |
| `initialize` | Миграции и первый администратор; завершение службы нормально |

Данные сохраняются в именованных томах Docker. Для обычной остановки и запуска:

```powershell
docker compose stop
docker compose start
docker compose ps -a
docker compose logs --tail 50 web indexer search-worker
```

`docker compose down -v` удаляет тома с данными, поэтому не используйте его для обычной остановки.

Пауза/продолжение загрузки с сохранением позиции:

```powershell
docker compose exec web python manage.py index_procurements --pause
docker compose exec web python manage.py index_procurements --resume
```

После изменений кода нужно пересобрать образ: исходники не подключены в контейнеры как редактируемый том.

```powershell
docker compose build web
docker compose run --rm --no-deps initialize
docker compose up -d
```

## Разработка и проверки

### Поисковые индексы и кэш кандидатов

Миграция `0012_search_projection_and_cache` добавляет компактный нормализованный текст, поля отбора и PostgreSQL-индексы `pg_trgm`/GIN. После обновления образа и миграций заполните их из уже сохранённых ответов API, без скачивания закупок:

```powershell
docker compose run --rm --no-deps web python manage.py backfill_search_projection
```

Новые и изменённые строки получают поисковые поля при сохранении. Прямое обновление JSON без пересчёта полей сбрасывает их триггером: такие записи проверяются прежним способом, а не исчезают из поиска. SQL выбирает кандидатов; точные правила слов, фраз, И/ИЛИ и исключений проверяются в Python.

Кэш хранит только ID кандидатов на 120 секунд, отдельно по пользователю и условиям. По умолчанию он выключен: локальный замер не показал заметного выигрыша поверх SQL-фильтрации. Изменения индекса автоматически меняют ревизию и отменяют использование старого кэша. Сроки и временные группы статусов проверяются при каждом поиске. Максимум — 10 000 ID на запись и 256 записей; более широкие поиски выполняются напрямую. SQLite использует резервный конвейер без PostgreSQL-предфильтров и кэша.

Для диагностики в `settings.py` доступны `SEARCH_DB_PREFILTERS` и `SEARCH_CANDIDATE_CACHE`. `scripts/profile_search.py` поддерживает `--reference` (прежний полный обход), `--no-cache` и `--warm-cache`. Диагностические результаты поиска откатываются; `--warm-cache` сохраняет только временный кэш кандидатов. Отчёты храните в игнорируемой `data/`.

Миграция `0013` добавляет частичный индекс для проверки незаполненных карточек: расчёт полноты базы не требует чтения JSON всех лотов при каждом поиске. PostgreSQL-соединения используют `cursor_tuple_fraction=1.0`, поскольку поисковый поток читается полностью. При сохранении изменившихся результатов повторно используются уже загруженные лоты, объявления и неизменившиеся заказчики; приоритет проверенных карточек сохраняется.

`scripts/compare_source_search.py --search UUID --output /app/data/source-comparison.json` выполняет сверку с живым публичным реестром госзакупок без изменения результатов пользователя. Поддерживает ИЛИ по терминам, статус, способ и предмет закупки; медицинские площадки не сравнивает. Отдельно показывает лоты из расширенных описаний и проверяет выборку дополнительных результатов по карточкам объявлений. Для запуска в Compose скрипты подключаются отдельным read-only volume, как при профилировании.

`scripts/compare_tenderbot_search.py --search UUID --output /app/data/tenderbot-comparison.json` сравнивает открытые госзакупки способом ЗЦП с Tenderbot API. Читает `TENDERBOT_API_KEY` из файла `--env-file` (по умолчанию `/run/tendersearch.env`); локальный `.env` подключайте в контейнер только для этого запуска read-only. Ключ, заголовки авторизации и настройки приложения в отчёт не записываются. Скрипт отдельно учитывает будущий приём, другие способы закупки и объединённые лоты; Самрук-Казына и MED/FMS исключены из этой сверки. Частичный обход при достижении `--max-pages` отмечается в отчёте.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[dev]'
.\.venv\Scripts\python.exe -m pytest
docker compose exec web python manage.py check
docker compose exec web python manage.py test tender_search.core
```

Локальные Django-тесты без PostgreSQL:

```powershell
$env:TENDER_SQLITE = '1'
$env:DJANGO_SECRET_KEY = 'local-test-only-key'
.\.venv\Scripts\python.exe manage.py test tender_search.core
```

`scripts/verify_*.py` проверяют работающую установку; некоторые создают поиски и временное избранное. Изучите сценарий перед запуском на рабочих данных.

## Версия «Госзакупки»

Прежняя база клиентов и сбор e-mail в этой версии отключены: страницы и экспорт недоступны, команда сбора заблокирована, сервис `lead-collector` исключён из Compose. Раздел «Администрирование» теперь предназначен только для управления пользователями и доступен всем пользователям с ролью «Администратор». Существующие таблицы сохранены для совместимости миграций.

## Доступ и секреты

Веб-порт привязан к `127.0.0.1:8000`, PostgreSQL и Redis наружу не опубликованы. Для внешнего доступа нужны HTTPS и настройка доменов/CSRF. `compose.tunnel.yaml` задаёт дополнительную веб-службу; сам туннель и локальный `data/tunnel.env` настраиваются отдельно.

В Git не включаются `.env`, рабочие базы, дампы, содержимое `data/`, скачанные документы и временные исследования API. `.env.example` содержит только заглушки. Резервные копии пользовательских данных и секреты передаются отдельно в зашифрованном виде.

Приложение читает публичные данные `zakup.gov.kz`. Подача заявок, ЭЦП и NCALayer не автоматизируются. Перед участием проверяйте актуальные условия на государственном портале.

## Раздельное обновление реестров и подробностей

`indexer` читает только страницы реестров активных лотов и объявлений. Новые/изменённые строки лотов сразу сохраняются для поиска. Реестр объявлений позволяет обнаружить лоты, отсутствующие в отдельном реестре лотов: их состав загружает `detail-indexer`. После окончания обоих реестров следующий обход начинается через 15 минут, круглосуточно.

Подробности обновляются отдельным процессом, через очередь `AnnouncementRefresh` в PostgreSQL. На объявление хранится одна задача: новые изменения повышают её приоритет и ревизию. Неизменённая запись не продлевает срок актуальности карточки. После успешной проверки следующая плановая проверка назначается через 6 часов; фактическое время зависит от очереди и доступности API. Оба процесса используют прежний общий предел — один запрос в секунду.

Ошибка карточки не задерживает реестры: повтор выполняется отдельно с увеличением задержки до часа. HTTP 404 исключает недоступные лоты; повторная проверка объявления — через сутки или раньше при изменении реестра. Карточки проверяются и при неизменном реестре, чтобы находить изменения в дополнительных описаниях. Истёкшие лоты не участвуют в поиске; исчезнувшие объявления снимаются после завершения обоих реестров. Избранное и его документы сохраняются.

Курсоры, задачи, ошибки и аренда задач хранятся в БД. После перезапуска процессы продолжают работу; ответ устаревшего запроса не может подтвердить более новую ревизию. Миграция 0015 сохраняет лоты и последнее время завершения, но начинает первый обход реестров заново для заполнения очереди. Перед миграцией остановите старый `indexer`, сделайте резервную копию БД и затем запустите оба процесса новой версии.

В административном блоке отдельно показаны время обхода реестров, очередь подробностей и число задач с ошибками. `ProcurementIndex.completed_at` означает завершение реестров; `index_coverage.ready` дополнительно требует обработки новых/изменённых подробностей. Первоначальная загрузка подробностей может занять часы. Поиск остаётся локальным. Перекрытие страниц и повторные обходы уменьшают пропуски при изменении выдачи портала; API с изменяемой offset-пагинацией не даёт гарантии единого снимка всех записей.

## Рабочее пространство и этапы работы

Раздел `/collections/` доступен каждому пользователю только для его подборок. Каждому сохранённому фильтру соответствует вкладка. «Сохранить» включает обновление подборки и Telegram-уведомления; создание и пересохранение подборки доступны только после подключения Telegram (активная личная привязка чата). Проверка выполняется в интерфейсе и на сервере; обычный поиск доступен без Telegram. Существующие Telegram-настройки при миграции не меняются. Кнопка сохранения возле «Мои подборки» включает/приостанавливает отслеживание и рассылку; Telegram можно отдельно выключить внутри подборки.

Обновления выполняются круглосуточно через `collection-monitor` и задачу `refresh_collection` в очереди `celery`; используются локальные данные, новых запросов к порталу не добавляется. Интервал — целые 1–12 часов. Пользователь также может обновить подборку вручную. Рассылки сохраняют окно 07:00–19:00 по Алматы.

«Все лоты» показывает текущие совпадения и сохранённые в работе позиции. Звезда или кнопка «В интересные» переводит новый лот в «Интересные». В карточке этого этапа вводится цена; единственная кнопка «Подать цену» атомарно сохраняет её, блокирует изменение цены/НДС и включает проверку итогов. Это отметка пользователя о фактической подаче, а не отправка заявки на портал. Этапы: «Интересные лоты», «Подали заявку», «Выиграли», «Проиграли», «Не участвовали», «Заключение договора», «Поставка», «Оплата». Ручные списки этапа и исхода удалены. Звезда сохраняется при продвижении по этапам. Избранное и Telegram-слежение за статусом используются общие с поиском; снятие звезды по-прежнему отключает слежение за статусом.

Лоты со звездой, включённым слежением или ручным этапом сохраняются после исчезновения из свежей выдачи. При первом обновлении также восстанавливаются отмеченные лоты из прежних поисков, явно связанных с этой подборкой. Неполный поиск добавляет результаты, но не удаляет прежние совпадения. Изменение фильтра помечает прежние совпадения как находящиеся вне выдачи, сохраняя позиции в работе; ревизия защищает от результата старого фонового задания.

Миграция `0016_collection_workflow` добавляет поля планировщика и таблицу этапов. После миграции пересоздайте `web`, `worker` и запустите `collection-monitor`. Временные фоновые результаты удаляются после переноса в подборку. Страница обновляется каждые 30 секунд; автоматическая замена откладывается, пока пользователь редактирует этап.

Миграция `0017_collection_notes_contract` добавляет этап договора и личные заметки `UserLotNote` (до 10 000 символов). Заметка принадлежит паре пользователь–лот, общая между его подборками и недоступная другим пользователям. Редактируется внутри карточки лота и не удаляется при удалении подборки. Автопереходы по статусу портала и автоархивирование пока не включены.

Звезда, Telegram-слежение и личная отметка «Сохранён в подборку» используют один источник состояния (`lot_state.py`) в таблице/карточках поиска, избранном, подробной карточке и подборках. Отметка появляется, если лот виден хотя бы в одной подборке текущего пользователя, и не меняет статус закупки на портале. При нескольких подборках удаление одной не снимает отметку, пока остаётся другая. Состояния открытых представлений синхронизируются после действий, при возврате во вкладку и раз в 30 секунд без сброса заметок; данные другого пользователя не используются.

Вкладка «Общая подборка» (`/collections/?profile=all`, также открывается по умолчанию) объединяет видимые лоты всех подборок текущего пользователя. Лоты и счётчики дедуплицируются по локальному идентификатору лота. Для каждой исходной подборки остаётся собственная форма этапа и результата; изменение одной не меняет остальные. Личная заметка, звезда и слежение общие для пользователя и лота.
Заметка в подробной карточке лота и в подборках использует одну запись `UserLotNote` текущего пользователя. POST `/lots/<id>/note/` сохраняет до 10 000 символов, допускает очистку заметки и не меняет избранное или слежение. Обновление карточки откладывается, пока заметка редактируется.

В таблице пользователей администрирования выводятся «Статус» подключения Telegram, «Telegram nick» и «Telegram name» по связке `TelegramSubscription` и `TelegramContact`. Доступ к сайту показан отдельной колонкой. Контакты без привязки к пользователю сохраняются в реестре, но не добавляют строки в таблицу пользователей. Обновляется входящими сообщениями; `/start` включает, `/stop` выключает отметку активности. Миграция `0018` переносит известные ID из `TelegramSubscription`; неизвестная дата первого обращения остаётся пустой. После миграции обновите `web` и `telegram`. Telegram API не предоставляет полного списка исторических подписчиков: доступны известные привязки и обращения, полученные этим экземпляром бота.

## Личная цена и НДС

`UserLotPrice` (миграция `0019`) хранит цену за единицу с НДС и выбранную ставку отдельно для пары пользователь–лот. POST `/lots/<id>/price/` доступен только для своего лота на этапе «Интересные» и означает «Подали заявку»: обязательная положительная цена фиксируется вместе с переходом. Повторное изменение/очистка после фиксации запрещены на сервере. До сохранения браузер и сервер независимо рассчитывают цену подачи без НДС и налог; деньги округляются HALF_UP до 0,01. Браузер использует целочисленные копейки BigInt, сервер — Decimal.

Расчёт доступен только для явно подтверждённого Госзакупа (`system.id=1`, противоречащие идентификаторы блокируют), проверенных способов 11/12/23/35/36/41 и подробной карточки с `is_combined=False` и единственным пунктом плана. Наличие данных в API Госзакупа само по себе не считается подтверждением площадки. Для одиночного лота из адаптера Госзакупа собственную цену с НДС можно зафиксировать и без подтверждения правила подачи; при противоречащих данных площадки показывается арифметический пересчёт нашей цены, но он не называется подтверждённой ценой подачи. MED/FMS, объединённые лоты и карточки без доказанного состава не получают форму ввода. Количество берётся из `plan_items[0].count`; неизвестное/некорректное количество не заменяется единицей. Обновление карточки сохраняет минимальный снимок этих полей; также используется проверенный кэш карточек.

Итог по лоту считается прямым способом: округлённая цена подачи × количество → сумма без НДС, затем НДС и итог с НДС. Отличие от введённой цены с НДС × количество показывается отдельно. Для новых цен автоматически применяется 16%; выбора ставки в интерфейсе нет, переданная клиентом ставка игнорируется. Сохранённая историческая цена использует зафиксированную ставку; калькулятор не определяет освобождение оборота от налога. Основание правил: https://wiki.goszakup.gov.kz/pages/viewpage.action?pageId=1311324 и https://wiki.goszakup.gov.kz/pages/viewpage.action?pageId=1311256 .

В персональных и общей подборке `sort=amount|-amount|start|-start|end|-end` сортирует всю выдачу перед пагинацией, пустые значения в конце. Параметр сохраняется при переходе между этапами, страницами и после изменения этапа.
Выбор этапа вручную убран на всех вкладках. Заметки редактируются только внутри карточки; небезопасные внешние адреса возврата не принимаются.


## Автоматические переходы и техспецификация (0020–0022)

После миграций обновите `web`, `worker`, `collection-monitor` и `telegram`. БИН компании хранится отдельно для пользователя в `CompanySettings`; задаётся в настройках. `LotOutcomeWatch` создаётся после «Подали заявку». Планировщик работает круглосуточно независимо от Telegram. Подтверждённые итоги проверяются по действующему протоколу конкретного лота: наш БИН победитель → «Выиграли»; наш БИН участник, другой победитель → «Проиграли». Отсутствие БИН, неоднозначный документ и неподдерживаемая площадка не считаются поражением. Смена БИН/версии протокола аннулирует устаревшую проверку. `OutcomeDelivery` устраняет повторную рассылку одного результата. Текущий адаптер итогов ограничен явно подтверждённым Госзакупом; живые ответы портала могут быть недоступны.

Лоты без подачи на этапах нового/интересного по истечении срока автоматически переходят в «Не участвовали». Продление срока возвращает только автоматически перенесённые позиции. Уже поданные заявки и подтверждённые итоги этот переход не затрагивает. Договор, поставка и оплата не выводятся из одного лишь истечения времени: переходы требуют подтверждённых данных публичного API по конкретному лоту и БИН пользователя.

Миграция сохраняет личные заметки и цены, объединяет старое ожидание с подачей и разделяет решение на выигрыш/проигрыш. Прежняя цена у интересного лота остаётся черновиком до явного нажатия «Подать цену».

Кнопка «Извлечь техспецификацию» в карточке запускает `extract_lot_specification`. Результат `LotSpecification` принадлежит пользователю. Обрабатываются связанные с лотом и общие документы объявления (последние помечены), исключаются файлы других лотов. Поддержаны текстовые PDF, DOCX, TXT; сканы требуют OCR, старый DOC — конвертации. Лимиты: 20 МБ, 80 страниц PDF, 8 документов, 160 000 символов каждого. Извлечение не добавляет лот в избранное и не включает Telegram.

На время тестирования на этапе «Подали заявку» доступно действие «Отменить отметку»: оно возвращает собственные поданные позиции в «Интересные», разблокирует сохранённую цену, отключает проверку итогов и аннулирует незавершённые проверки/ожидающие уведомления. После подтверждённого исхода или перехода к исполнению отмена недоступна. На портал эти действия ничего не отправляют.

Обновление уже установленной или распакованной версии другим ИИ-агентом: [ТЗ по обновлению из GitHub](docs/AGENT_UPDATE.md). Инструкция включает приватный доступ, вариант ZIP без `.git`, сохранение действующих томов, миграции и критерии приёмки рабочего пространства.


### Автоматическое исполнение договора

Миграция `0025_contract_watch` добавляет личную проверку договоров. После подтверждения победы по БИН монитор раз в час проверяет договоры Госзакупа (system=1), независимо от способа закупки. Подписание поставщиком (status=18) переводит в «Заключение договора», подписанный/действующий договор с подтверждённой датой — в «Поставка». Факт исполнения всех предметов именно этого лота переводит в «Оплата». Статус договора «Исполнен» вместе с фактом исполнения и полной оплатой каждого предмета переводит в архив. Аванс без исполнения не завершает поставку.

«Выиграли» и «Проиграли» — фильтры результата: выигранный лот остаётся видимым после перехода к договору, поставке, оплате или в архив. На карточке указан текущий этап. Данные разных пользователей и их БИН изолированы. Без БИН показывается общее напоминание со ссылкой на настройки.

Архив останавливает проверки; восстановление возобновляет их. Lease/generation и повторная проверка БИН, актуального протокола и этапа не позволяют применить устаревший ответ. Повторная проверка итогов сохраняется на этапах исполнения; пересмотр результата не откатывает фактическую поставку, но останавливает автоматическое продвижение до нового подтверждения победы.

Ограничения: только однозначный основной договор Госзакупа и точная связь предметов с лотом; допсоглашения, несколько договоров, обжалование, неполные реестры, неподтверждённые суммы/даты требуют ручной проверки. Медицинские площадки и Самрук автоматикой договоров пока не охвачены. Никакие заявки, подписи, договоры или платежи на внешнем портале не отправляются. Ручные подтверждения этапов сохраняются как резервный вариант.


Проверка участия теперь запускается автоматически для интересных лотов после окончания приёма, без ручной отметки о подаче. Пока протокол не подтверждён, лот остаётся в интересных. Наш БИН победил — ожидание договора; наш БИН участвовал и победил другой — проигрыш. Отсутствие БИН считается неучастием только после подтверждения полноты списка участников. Ошибки, отмена закупки, неизвестные форматы и отсутствие итогов сохраняют этап для дальнейшей проверки. Ранее автоматически закрытые интересные лоты включаются в такую проверку; ручные отклонения — нет.

## Восстановление пароля и подтверждение email

Миграция `0053` добавляет подтверждения email, общие для всех веб-процессов ограничения попыток и очередь служебных писем. Примените миграции перед обновлением веб-сервера и фоновых служб.

- `/password/reset/`: запрос одноразовой ссылки на 1 час; ответ одинаков для существующего и неизвестного email. После смены пароля старые сеансы становятся недействительными.
- Новая самостоятельная регистрация требует подтверждения email для рабочих разделов и личных фоновых задач. Письмо действует 24 часа; переход показывает кнопку подтверждения, только POST подтверждает адрес. Повторная отправка отменяет старую ссылку. 14 дней отсчитываются от регистрации.
- Существующие и созданные администратором аккаунты сохраняют доступ без принудительной проверки. Это исключение не означает, что их email подтверждён.
- Вход: до 5 попыток для пары IP/логин за 15 минут, до 30 с одного IP за 15 минут и до 50 на логин за час. Запросы сверх лимита получают HTTP 429 и Retry-After. Регистрация: 5 запросов/IP/час; восстановление и повторные письма: до 3 на адрес/аккаунт и 10 на IP за час. Успешные попытки также учитываются.

Сервис `auth-mailer` отправляет письма из очереди и повторяет отправку при временном сбое SMTP. Ошибка не теряет регистрацию. Команда `python manage.py send_auth_mail --once` обрабатывает доступную очередь один раз. Завершённые задания очищаются от адреса и nonce, удаляются через 7 дней. Страницы авторизации не кешируются и не индексируются; ссылки с токенами исключены из журналов запросов.

По умолчанию письма остаются в локальном Mailpit: `http://localhost:8025`. Он доступен только с этого компьютера, SMTP-порт наружу не опубликован. Это тестовая почта, **на реальные ящики письма не доставляются**. Запуск: `docker compose up -d mailpit auth-mailer`. После пересборки приложения обновите также `web`, `worker`, `search-worker`, `collection-monitor` и `telegram`.

Для реальной доставки задайте в `.env` параметры `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS` или `EMAIL_USE_SSL` и разрешённый SMTP-провайдером `DEFAULT_FROM_EMAIL`, затем пересоздайте `auth-mailer`. TLS и SSL одновременно не включают. Секреты не коммитятся. `AUTH_SITE_URL` — фактический доверенный адрес приложения для ссылок, отдельно от будущего SEO-домена `PUBLIC_SITE_URL`. По умолчанию используется localhost с `WEB_PORT`; `tunnel-web` задаёт свой HTTPS-адрес. После смены адреса запросите новое письмо. Не публикуйте интерфейс Mailpit через туннель.

`AUTH_TRUST_CLOUDFLARE_IP=1` включён только для изолированного `tunnel-web`, который не имеет опубликованных портов и получает запросы через Cloudflare. Для обычного веб-сервера заголовки клиентского IP игнорируются; при другом reverse proxy требуется отдельно настроить доверенную цепочку прокси.

После окончания приёма лот автоматически покидает этап «Подготовка заявки»: незавершённое заполнение отменяется, а личный этап переходит в «Интересные лоты» с проверкой итогов по БИН. Это исправляет также ранее отменённые записи очереди. Сохранённая подготовка и подтверждённые сведения портала остаются в истории; «Не участвовали» выставляется только после подтверждения отсутствия участия по полному протоколу. Уже поданные заявки, договоры, поставки и оплата сохраняют свои этапы.

Извлечение техспецификаций по кнопке использует отдельную очередь Celery `specifications` и сервис `specification-worker`. Повторное получение готового личного текста не ставит задание; полный актуальный общий индекс документов также можно использовать сразу после запроса пользователя. POST возвращает готовый блок текста одним ответом. «Обновить с портала» явно запускает повторную проверку, сохраняя прежний текст на экране. Фоновая индексация остаётся в общей очереди; ограничитель запросов к источнику общий для всех воркеров. После обновления запускайте также `specification-worker`.

## Защита данных пользователей

Загруженные акты приёмки личные: список и скачивание доступны только владельцу, включая прямые ссылки с идентификатором файла. Публичные документы портала сохраняют прежнюю общую политику хранения. Раздел клиентской базы и экспорт требуют роли администратора (`is_superuser`), одного `is_staff` недостаточно.

Ответы авторизованным пользователям получают `Cache-Control: private, no-store`. В HTTPS-сервисе включены Secure cookies, перенаправление на HTTPS и HSTS на 1 час, без preload и includeSubDomains. Локальный HTTP остаётся доступен только через loopback. Разбор DOCX запрещает DTD и XML-сущности через defusedxml; прежние ограничения размера, числа файлов в архиве, PDF-страниц и времени воркера сохраняются. Сборка обновляет pip до ветки 26.3+.

Проверка безопасности 12 ноября 2026 года включала разграничение прав, CSRF и вход, изоляцию файлов, ограничения внешних загрузок, настройки Docker/Django и сверку Python-зависимостей с PyPI Advisory Database. Проверка зависимостей не заменяет сканирование ОС образа и внешнее тестирование развёрнутой инфраструктуры. Новая версия и зависимости должны проходить эти проверки повторно.

После подтверждения расширением готового черновика с номером заявки и сохранённым описанием лот автоматически переходит из «Подготовка заявки» в «Ожидаем итоги». Звезда и сведения черновика сохраняются; счётчики обновляются после ответа расширения. Новый этап доступен в общей и личных подборках. Цена, обеспечение, подписание и отправка остаются действиями пользователя на Госзакупе; подтверждённая подача переводит лот в «Подали заявку». Итоги готового черновика проверяются после окончания приёма: подтверждённая победа ведёт к договору, проигрыш — в «Проиграли», полное подтверждение отсутствия участия — в «Не участвовали». Неизвестные или неполные итоги сохраняют ожидание. Если срок продлён, проверка итогов приостанавливается. Проверка наличия черновика и возврат в подготовку после подтверждения его отсутствия доступны в новом этапе. Миграция 0054 переносит только ранее подтверждённые готовые черновики с совпадающим БИН из подготовки.

Этапы CRM взаимоисключающие: победа в протоколе переводит лот в «Заключение договора», а «Выиграли» содержит только завершённые поставки с актом и подтверждённой полной оплатой. Из «Выиграли», «Проиграли» и «Не участвовали» фоновый монитор переносит лоты в архив через 30 дней после входа в соответствующий этап. Дата stage_entered_at меняется только при смене этапа; повторные проверки итогов и обновления подборок не продлевают срок. После восстановления из архива отсчёт начинается заново, история и дата завершения сохраняются. Миграция 0055 использует updated_at как консервативную исходную дату для старых записей и корректирует прежние значения победы/оплаченного архива.

Личные страницы повторно проверяют аккаунт при возвращении фокуса и восстановлении из истории. Пока проверка не завершена, прежние поля скрыты и недоступны. При смене аккаунта личный DOM удаляется, страница открывается заново GET-запросом; старые AJAX-запросы и формы блокируются сервером по идентификатору аккаунта. Расширение 0.17.0 отдельно проверяет пользователя исходной вкладки перед выдачей пакета и действиями на портале; установленные копии необходимо обновить через настройки и перезагрузить открытые страницы. Пагинация поиска, избранного, CRM, клиентской базы и открытого каталога использует номера с выделением текущей страницы, крайними номерами и многоточием; фильтры и сортировка сохраняются.
